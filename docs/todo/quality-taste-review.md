# Architecture and code-quality review

Reviewed 2026-11-13. Recommendations, not an approved implementation specification.

## Assessment and scope

Roadie has a sound basic architecture: declarative build steps, a separate execution engine, and platform-specific operations behind `roadie.system`. Keep that shape. The best improvements are tighter ownership of execution state, explicit extension contracts, and consolidation of a few proven shared operations. A general framework rewrite would add risk without addressing the most concrete problems.

Reviewed Roadie's engine and build primitives, relevant tests and specification, and Niva's root, notation, desktop, forge, jammer, and acceptance `build.py` files. Followed their Python dependencies into packaging, vendor installation, services, test reports, and build evidence. This is a review of Niva's build/tooling architecture, not an exhaustive review of its Rust application, renderer, or frontend internals. Existing uncommitted changes in both repositories were left intact.

References below use repository-relative paths and symbol names; Niva paths are relative to `~/personal/niva`. Priorities mean: **P1** correctness or resource risk; **P2** worthwhile architectural improvement; **P3** smaller cleanup. Effort is relative, not an estimate of days.

## Findings

### 1. Failed comparisons can be mistaken for equality

**Evidence:** Roadie [`generated.py`](../../src/roadie/build/generated.py), `_git_hash` and `same_as_git_stores`; [`file.py`](../../src/roadie/build/file.py), `File.publish`.

`_git_hash` returns `None` for a nonzero Git exit. `same_as_git_stores` compares the two results directly, so two failures become `None == None`. After tracking succeeds, a failing clean filter or another hash-command failure can therefore make different generated bytes appear equivalent. `File.publish` then returns the existing destination, including in locked mode.

**Recommendation:** Make unsuccessful hashing raise a path-specific `RoadieError`. Keep “different content” distinct from “could not compare.” Share command mechanics where useful, but preserve operation-specific error context.

**Acceptance:** Exercise first-hash failure, second-hash failure, both failures, empty successful output, and valid line-ending normalization. Assert visible failure and an unchanged destination when hashing fails. Existing Git-tracking failure coverage does not cover this comparison branch.

**Verification:** A mock-based probe of the actual `same_as_git_stores` function returned `True` when both subprocess results had exit status 1. This confirms the comparison defect; an end-to-end failing-filter fixture remains to be added.

### 2. Command diagnostics retain all output even when only a tail is needed

**Evidence:** Roadie [`step.py`](../../src/roadie/engine/step.py), `Step._cmd`; [`prefix.py`](../../src/roadie/engine/prefix.py), `read_lines`.

`_cmd` accumulates every stderr line in `stderr_parts`. It also accumulates piped stdout when parallel output requires a reader, even if `capture_output=False`; that stdout is not returned. The error message uses only a 2,000-character stderr tail, but the implementation retains the entire stream until command completion. Large compiler/test output can consume substantial memory, multiplied by concurrent jobs. State is eventually released, so this is unbounded retention during a command rather than proof of a permanent leak.

**Recommendation:** Separate streaming, bounded diagnostic tails, and explicitly requested capture. Do not collect stdout merely to prefix it. For full capture, define a documented size policy or spool to a run-owned artifact; preserve the stdout contract used by Cargo JSON and OpenAPI generation. Bound partial lines as well as completed lines.

**Acceptance:** Run simultaneous noisy commands with and without capture, a very long line, failure, and interruption. Verify streamed output, useful error tails, bounded retained state, and cleanup of any spool files.

### 3. Niva's cache declarations omit some code and environment dependencies

**Evidence:** Roadie [`fingerprint.py`](../../src/roadie/engine/fingerprint.py), `_code_hash`; Niva `forge/niva/vendor/pdfium.py:Pdfium`, `forge/niva/vendor/common.py`, `forge/niva/macho.py`, `jammer/build.py:WEB`, and `jammer/ops/jammer_build/steps.py:WebSchema`.

Roadie hashes modules defining a step's class hierarchy and all Roadie modules. It does not recursively hash arbitrary imported helpers, as its specification explicitly states. A `Pdfium` step calls `common.downloaded_archive` and `require_archs`, but declares only tag and platform fields. Changing those helper implementations alone does not enter that step's code hash. Running forge tests separately is not an invalidation edge to the vendor result.

Niva's `WEB` input includes source trees, manifests, and the pnpm lockfile, but no `NodeEnv`. Node/pnpm version changes are therefore not declared inputs for these web checks and bundles. `WebSchema` tracks two package manifests rather than the full toolchain environment. Roadie already provides `NodeEnv` and `PnpmPackage` for this purpose.

**Recommendation:** Audit custom steps for every helper module and tool environment that affects their output. Declare narrow `Files` inputs for imported implementation helpers and use existing Node inputs where appropriate. Avoid automatically traversing all Python imports: that would expand invalidation unpredictably and change the documented contract.

**Acceptance:** Change only a helper implementation, only Node/pnpm versions, and only a transitive workspace package. Assert the intended consumers rerun; unrelated consumers should stay reusable. Also test unavailable tool executables and invalid workspace metadata. These are static dependency findings, not a measured stale-cache incident.

### 4. Execution state lacks a single, enforceable owner

**Evidence:** Roadie [`run.py`](../../src/roadie/engine/run.py), `_run_steps`, `_schedule`, `_execute_step`, `_run_one`, `_kept`, and `_start_one`.

The executor passes overlapping bundles of mutable state through many functions: live values, outputs, started/finished/running sets, deferred guards, report state, locks, and requested targets. Several functions reach into `Run._values` directly. Immediate and deferred execution separately implement announcement, timing, reporting, exception translation, and value registration. A new lifecycle rule consequently needs coordinated changes in several paths.

This is a responsibility problem, not simply a complaint about the module's length. A large replacement `Executor` class containing every current function would preserve the same coupling.

**Recommendation:** Introduce internal owners around existing invariants: scheduling state owns readiness and synchronization; a resource registry owns value registration and reverse-order teardown; a record store owns restore/save; a small orchestrator connects them. Keep public `Run` focused on the value/artifact interface available to steps. Extract common execution stages only where immediate and deferred semantics agree—deferred startup intentionally differs from normal publication/reuse.

**Acceptance:** Preserve the existing scheduler, jobs, service, reporting, and teardown suites. Add interaction tests for a shared deferred service, concurrent consumers, consumer failure, publish/report failure, interruption, and teardown failure. Assert exactly-once cleanup and visible primary/secondary errors. Use events/barriers and bounded status waits, never timing sleeps.

### 5. The convenient Step DSL also makes incidental mutation architectural

**Evidence:** Roadie [`step.py`](../../src/roadie/engine/step.py), `__new__`, `attributes`, and `dependencies`; [`fingerprint.py`](../../src/roadie/engine/fingerprint.py), `_classify`; Niva `jammer/build.py`, `snap_viewer.viewer_bundle = viewer_bundle`.

`Step.__new__` installs engine metadata; `attributes()` discovers all other instance fields and treats them as declaration data. Adding a runtime cache or collaborator can unexpectedly change fingerprints or fail validation. Dependency discovery and fingerprint classification separately interpret those fields. In Niva, a `RustBinary` gains a required ordering dependency through an undeclared attribute assignment after construction. It works under the current DSL, but the class signature does not communicate the dependency.

**Recommendation:** Preserve concise dataclass declarations while centralizing attribute classification in one internal representation used by planning, fingerprinting, and dry output. Provide a documented way to declare ordering/build inputs on binary steps, then construct the viewer binary with its bundle dependency. Keep runtime collaborators in run-owned state rather than adding arbitrary instance fields. Consider validating and freezing declarations after loading, not during build-file composition.

**Acceptance:** Preserve included-result semantics, reserved-name errors, tuple inputs, and deterministic order. Test that the viewer bundle precedes compilation, that its change invalidates the binary, and that accidental runtime state cannot silently alter the graph. Any public declaration-model change needs specification approval first.

### 6. Niva reaches across Roadie's intended extension boundary

**Evidence:** Niva `forge/niva/package.py` imports `_executable_from_cargo_messages` from `roadie.build.rust`; `jammer/ops/jammer_build/steps.py` imports `RunningProcess`, `available_port`, and `port_is_busy` from the engine. Roadie's [`build/__init__.py`](../../src/roadie/build/__init__.py) already acts as a public facade.

The private Cargo-parser import is a concrete compatibility dependency. The process imports are not underscore-private, but they bypass the build facade and bind consumer code to engine organization. Roadie cannot freely refactor these internals without coordinating Niva changes.

**Recommendation:** Promote the narrowly reusable Cargo artifact parser and service-construction capabilities to documented extension APIs, with explicit result/error contracts. Keep `Step._cmd` as a delegating compatibility helper while moving process execution mechanics out of the declaration class. Use a lower-level command adapter for metadata queries; do not require constructing a fake step to query a tool.

**Acceptance:** Cover multiple/no executable artifacts, malformed messages, missing tools, Windows command resolution, startup failure, timeout, cancellation, and process cleanup. Add a Niva consumer test against public imports. Expand Roadie's layer test to check prohibited system-to-engine/build imports; avoid a blanket ban on every engine import until the supported extension contract is defined.

### 7. Two JUnit parsers have already diverged

**Evidence:** Roadie [`pytest_step.py`](../../src/roadie/build/pytest_step.py), `_junit_failures`; Niva `jammer/ops/jammer_build/junit.py:read_junit` and `steps.py:ContractFuzz`.

Roadie's reader extracts unqualified testcase failure/error messages. Niva's reader also handles XML namespaces, nested suites, element text, captured output, invalid roots, and readable parse errors. They also differ in testcase naming and whether multiple failures become separate entries. Copying either parser over the other would change user-visible output.

**Recommendation:** Put a shared JUnit reader next to Roadie's `TestResults`, with deliberately chosen compatibility behavior. Keep pytest's exit-status policy and Schemathesis's command/report reconciliation in their respective runners. Share parsing, not an overly general test-runner hierarchy.

**Acceptance:** Reuse both sets of fixtures and add namespaced/nested suites, missing or malformed reports, multiple failure children, captured logs, nonzero exit with a passing report, and stale report files. Resolve naming and aggregation differences explicitly before migration.

### 8. Release mixes format policy and irreversible workflow

**Evidence:** Roadie [`release.py`](../../src/roadie/build/release.py), `PyProject`, `CargoManifest`, `PackageJson`, `_Manifest`, `_version_or_none`, and `Release.build`.

The module owns three manifest formats, lockfile updates, version selection, Git preconditions, local edits, commit/tag creation, and push. `_Manifest` reaches into each source's private `_file` method. Directory discovery catches every `RoadieError` from version reading and treats it as “no version,” conflating intentionally versionless manifests with invalid manifests. Publication proceeds through local mutations before the remote atomic push; atomic push does not make those local operations transactional.

**Recommendation:** Define a small manifest protocol for public path/read/edit operations; separate format-specific editors from release orchestration. Produce and validate a release plan before mutation. Distinguish “version absent” from invalid/unreadable input. Specify recovery after lockfile-update, commit, tag, or push failure; do not add automatic rollback of user work without an explicit policy.

**Acceptance:** Retain existing multi-manifest, formatting, lockfile, and Git-precondition tests. Add mixed valid/malformed directory sources, failure while updating a later manifest, and rejected push after local tag creation. Assert the exact surviving state and actionable recovery message.

### 9. Jammer services combine process, storage, and application configuration

**Evidence:** Niva `jammer/ops/jammer_build/steps.py`, `RunningService`, `JammerDevServer`, and `WebDevServer`.

`RunningService` inherits `RunningProcess` and adds storage ownership; `JammerDevServer` chooses ports, creates storage, builds application configuration, starts a process, and translates ownership. `WebDevServer` calls its static configuration/storage methods despite not being that kind of server. Both normal teardown and startup-failure cleanup use `shutil.rmtree(..., ignore_errors=True)`, so failed temporary-directory cleanup is invisible.

**Recommendation:** Extract a small typed development configuration and a storage owner with an explicit cleanup contract. Compose those with the process handle. Keep Jammer-specific environment values in Niva. When cleanup fails, preserve the startup/command failure as primary but surface the storage path and cleanup failure as secondary evidence.

**Acceptance:** Cover temporary versus persistent storage, occupied ports, configuration failure, startup/readiness failure, interrupted startup, normal stop, and cleanup failure. Existing service tests are a strong starting point; assert both process and directory ownership, not only stop calls.

### 10. Small shared helpers are justified; broad utility modules are not

**Evidence:** Niva `forge/niva/package.py:workspace_version` and `forge/forge/evidence.py:workspace_version` independently parse the same Cargo workspace version with different failure messages. `jammer/build.py` changes `config(base_dir="..")` midway; `PythonModels.__post_init__` locates the repository from the process working directory via `forge.environment.repository_root`.

**Recommendation:** Consolidate Niva's static workspace-version reader with a single path-based contract. Resolve step-local repository inputs from the step's captured base directory rather than ambient cwd. Group declarations by path context or use small factories that make the context explicit. Preserve the already useful `cargo_check` and shared vendor-download helpers.

Do not combine environment loaders merely because both read dotenv files: Niva's `environment_from_files` lets process values win, whereas Roadie's command environment gives configured env files precedence. Likewise, Cargo and pnpm dependency traversal may share a small graph helper eventually, but their workspace discovery and invalidation policies should remain distinct.

**Acceptance:** Test alternate invocation directories, included build files, missing/malformed manifests, and the existing environment precedence rules.

## Refactoring order and ownership

1. **Fix failure and retention defects in Roadie:** Git hashing first, then bounded output. Keep these changes independent of structural work.
2. **Repair Niva input declarations:** helper code and Node environment coverage; verify invalidation behavior before moving code.
3. **Extract proven shared contracts into Roadie:** JUnit reading and Cargo artifact parsing. Migrate Niva consumers and verify compatibility.
4. **Improve declaration and execution internals separately:** explicit binary dependencies and shared attribute classification first; scheduler/resource ownership afterward.
5. **Refactor release and Jammer services in their owning repositories:** preserve visible behavior except explicitly approved failure-path corrections.

Keep Niva's release asset names, Tauri version-pair policy, native SDK layouts, deployment evidence, and application configuration in Niva. Keep general build execution, process lifetime, artifact decoding, and test-result parsing in Roadie. No new cross-repository utility package is warranted by the reviewed duplication.

## Existing strengths and validation limits

Preserve the engine/build import boundary, platform isolation and banned-platform-API lint rules, typed input/value models, thin build-file composition, run-scoped input cache, and behavioral tests for resource teardown and release preconditions. The optional lifecycle hooks on `Step` are a reasonable extension mechanism; replacing each with a separate interface would add complexity unless callers actually need those narrower capabilities.

Validation: `.venv/bin/python -m pytest tests/test_layers.py tests/build/test_file.py tests/build/test_pytest_step.py -q` passed all 22 tests. The targeted Git-hash probe described above also ran. This report otherwise relies on source review. It does not claim a full test pass, a concurrency stress test, or performance measurements. No builds, releases, deployments, or live acceptance actions were run.

### G1 — P2: Narrow the platform boundary and remove duplicated Windows policy

**Author observation 1: confirmed.** `src/roadie/system/command.py:53` defines `batch_command_line` without a private prefix, and `src/roadie/system/__init__.py` explicitly re-exports it in `__all__`. Production callers found in Roadie use it only inside `prepare_command`; external callers should use the portable operation. Rename it `_batch_command_line` and remove the facade export unless an intentional external compatibility commitment is identified. Keep tests of the quoting algorithm, but test the public portable operation as well.

**Author observation 2: narrower than a runtime portability violation.** `src/roadie/engine/step.py:234` is inside `_cmd`'s Windows-specific docstring. `_cmd` already calls `prepare_command(args, env)` before `Popen`; Windows detection, resolution, and batch quoting live in `system.command`. `Popen` itself is cross-platform. The confirmed issue at the cited location is duplicated platform-policy documentation and an overly broad command-helper responsibility, not an unguarded Windows implementation there.

Move the detailed quoting rules to their system implementation/specification and have the step helper describe its portable behavior. As part of finding 6, delegate process launch/termination mechanics through portable system operations while retaining step environment, output, and error context in the engine. In particular, inspect `_cmd`'s direct `terminate()/wait()` cancellation fallback when consolidating process ownership. Moving code alone does not prove cancellation behavior correct.

**Verify:** Public command behavior on native Windows and POSIX; quoting/refused characters; missing executable; cancellation and child cleanup. Keep the platform API lint rules, and extend import-boundary tests. A successful lint run alone cannot catch an inappropriate platform-specific facade export.

### G2 — P1: Global caches outlive the classes and runs they describe

**Rule:** Release lifetime-scoped state; otherwise provide tested reclamation or a documented byte ceiling.

**Evidence:** `src/roadie/engine/step.py:_value_adapters` is a process-global dictionary keyed by class objects. `_value_adapter` inserts each encountered class, including entries with `None` adapters; there is no removal path. Repeated build-file loads can create new step classes. A local probe created three temporary `Step[int]` subclasses, populated the adapters, dropped local class references, and ran garbage collection: all three classes remained alive and all three entries remained in the cache.

`src/roadie/engine/records.py:_reported_unreadable` similarly retains every distinct bad record path for the process lifetime. Its once-per-process warning suppression can also hide a recurring failure in later runs using the same process. Neither cache has a defined byte ceiling. A short-lived CLI process bounds the duration, but not the supported in-process usage.

**Recommendation:** Prefer run/load-scoped adapter state or an explicitly bounded cache with a justified ownership model. A weak-key dictionary alone is insufficient if an adapter value strongly references its key; prove collection. Scope record-warning deduplication to a run/read operation and release it when that owner ends.

**Verify:** Repeated load/execute/discard cycles, including failure, release temporary classes and warning paths. Verify a corrupt record is reported once within a run and again in a later run. Keep retained-state checks behavioral, not merely assertions that a reset helper was called.

### G3 — P2: A service test uses elapsed time as synchronization

**Rule:** Never fix asynchronous issues with delays; use status checks with a timeout.

**Evidence:** `tests/build/test_service.py:test_ctrl_c_stops_a_requested_service_that_outlives_it` waits in `while not started` without a deadline, then sleeps an additional 0.5 seconds before raising SIGINT. The extra delay assumes the executor has reached the intended wait state. A startup failure can leave its daemon thread polling indefinitely.

**Recommendation:** Signal an explicit event when the requested service enters its serving/wait phase, await it with a timeout, and then interrupt. Ensure the coordinating thread terminates on both success and failure. Review the nearby `Sleeper.wait` fake's five-second delay as well; use a controlled blocking primitive to model a running service.

**Distinction:** A bounded loop checking a readiness file, process state, or health endpoint is not the same defect merely because it sleeps between observations. Likewise, a subprocess fixture intentionally staying alive is not itself a readiness workaround. `tests/engine/test_derived.py:test_sigterm_during_a_slow_step_names_it_and_exits_130` already demonstrates bounded observable-state polling.

**Verify:** Exercise delayed startup and startup failure deterministically, without increasing sleeps; assert no coordinator thread remains after the test.

### G4 — P2: Record diagnostics expose parser internals

**Rule:** Error messages should name user-visible inputs/actions rather than internal offsets or algorithm state.

**Evidence:** `src/roadie/engine/records.py:load_record_at` passes `str(JSONDecodeError)` through `_unreadable`. `tests/engine/test_run.py:test_unreadable_record_is_ignored_and_the_step_rebuilds` explicitly expects `Expecting value: line 1 column 1 (char 0)`. This is a tested behavior that conflicts with the global message guideline. Pydantic validation messages are also passed through and should be reviewed for product-facing wording.

**Recommendation:** Retain the record path and recovery action, e.g. `ignoring unreadable record <path>: invalid JSON; rebuilding affected steps`. Translate structural validation failures into similarly stable terms. Preserve the visible warning and the documented rebuild behavior; do not convert this recovery path into a silent catch or an automatic fatal error.

**Verify:** Invalid JSON, invalid record structure, unreadable files, unsupported record versions, and repeated reads. Assert useful path/action text without parser offsets. Update both the relevant specification wording, if present, and tests together.

### G5 — P2: Restricted target validation lives at the CLI edge

**Rule:** Domain rules must remain effective when another caller bypasses the CLI.

**Evidence:** `src/roadie/cli.py:_one_requested` rejects selecting multiple distinct `once_per_run` targets, but `src/roadie/engine/run.py:execute` does not apply that validation. The scheduler uses the flag to defer each restricted target behind other unfinished work. A direct-engine probe with two independent restricted targets failed with `cannot schedule the plan`, rather than the CLI's actionable message naming both targets. The engine therefore fails indirectly after entering execution instead of rejecting the invalid selection at its boundary.

**Recommendation:** Move shared target-combination validation into engine planning/execution before setup or commands can run. Let the CLI retain syntax parsing. Preserve the existing rule and wording rather than inferring a new meaning from the flag's name. Review the CLI-only `--report`/dry-run prohibition separately to decide whether it is a CLI contract or a domain invariant; that classification is not settled here.

**Verify:** Call the engine directly with two restricted targets plus a setup step and assert early failure with no setup side effects. Cover one restricted target mixed with ordinary targets, aliases of one target, and dependency-connected selections.

### G6 — P3: Python organization and documentation have explicit convention deviations

- **Initializer contents:** `src/roadie/build/__init__.py` and `src/roadie/system/__init__.py` assign `__all__`, contrary to the literal “only extra imports, or empty” rule. `__all__` is useful here, especially for the supported wildcard build DSL, so removing it mechanically can change exported names. Keep re-export selection explicit through imports and test the public namespace, or have the author approve a narrowly documented exception. This review does not assume such an exception already exists.
- **Canonical module order:** Classes follow top-level functions in `engine/step.py`, `engine/graph.py`, `build/rust.py`, `build/release.py`, and other modules; Niva's `forge/forge/evidence.py` and vendor modules do the same. This conflicts with imports → variables/classes → functions. Reorder during related edits, checking definition-time references and decorators; keep cosmetic moves separate from risky lifecycle changes.
- **Conditional imports:** Niva `forge/forge/checks.py` imports from `forge.build_helper` inside `run_weekly_cargo_cleanup` and `CargoCleanup.build`. There is a real current reason for deferred loading: `build_helper` discovers the repository and creates CLI-related state at import time. Do not label these imports unjustified without addressing that dependency. Extract side-effect-free path/command helpers so the cleanup domain can import them normally.
- **Callable documentation:** Examples such as `Step._reports_reused` (“True when…”), `generated.tracked_files` (“Tracked files that…”), and Niva's `cli_archive` (“The CLI archive name…”) do not use imperative function-docstring style. Use “Return…” where documentation adds a contract, and remove trivial restatements. Class descriptions may appropriately describe the represented concept.
- **Test layout:** Move or split `tests/engine/test_batch.py` so pure command-resolution/quoting tests mirror `system/command.py`; keep step/CLI integration tests at their appropriate layer.

The production AST scan covered all Roadie modules plus Niva's `forge/forge`, `forge/niva/vendor`, and `jammer/ops/jammer_build`. It identified initializer assignments, function-local imports, classes following functions, and return-annotation presence. It did not certify import grouping, every parameter annotation, or every docstring. Plain dictionaries used as lookups are not automatically violations of the preference for structured models; execution-state and release-plan records are the stronger candidates described earlier.

## Step encapsulation and single-responsibility review

Reviewed 2026-11-14 against the current `src/roadie/engine/step.py`, Roadie's production subclasses, and the Niva build/tooling subclasses examined above. This section traces actual callers and overrides; it is not a runtime coverage measurement.

**Conclusion:** No, the instance variables and methods are not uniformly used by subclasses. Some common state is legitimately consumed by the engine on their behalf. The stronger architectural concern is that one base class combines declaration, loader identity, per-run environment, persistence, presentation, and process execution, while its reflection-based declaration model makes normal private subclass state difficult to encapsulate.

### Instance-variable ownership

`Step.__new__` creates eight fields on every instance, including dataclass subclasses whose generated constructors do not call a base initializer.

| Field | Actual owner/use | Subclass need | Recommended home |
|---|---|---|---|
| `serial` | Loader chooses the last-constructed default result | No direct reads in reviewed production subclasses | Loader/declaration identity |
| `name` | Loader assigns display identity; display/errors consume it | Some Niva subclasses read it; many use `_label()` | Read-only label view over loader metadata |
| `variable` | Loader assigns record/artifact identity; executor reads it | No direct reads in reviewed production subclasses | Loader metadata / record key |
| `build_dir` | Captured at creation, assigned during naming; records/artifacts use it | No direct reads in reviewed production subclasses | Loader metadata |
| `build_variables` | Loader assigns the set of live build-file names; record writer prunes obsolete entries | No direct reads in reviewed production subclasses | Build-file/record-store metadata, not each step's public state |
| `base_dir` | Captures path context; fingerprinting and command execution use it | `Release`, Niva packaging/evidence/tests, and `resolve()` clients use it | Immutable declaration context, exposed through a read-only property/helper |
| `env_files` | Captures configuration; executor reads it to construct the environment | No direct reads in reviewed production subclasses | Immutable declaration context |
| `env_values` | Executor overwrites it at run start; fingerprinting and command helpers read it | No direct reads in reviewed production subclasses | Per-run execution context |

Absence of a direct subclass read does not make a field unnecessary: a pure step's environment still participates in fingerprinting under the current specification. It does mean engine-owned data need not be mutable public fields on every user-defined step.

`env_values` has a particularly weak ownership boundary. The resolved environment belongs to an execution, yet remains attached to the declaration after execution ends. `run_scope()` releases its own caches, not this dictionary. Retaining a graph therefore retains its last resolved environment. Move this state with the run rather than adding another reset convention to subclasses.

### Method families and actual usage

| Methods | Where behavior is needed | Assessment |
|---|---|---|
| `build(run)` | All concrete step kinds, directly or through inheritance | Essential polymorphic contract |
| `attributes()`, `dependencies()` | Engine planning/fingerprinting; `_Included` overrides both | Common declaration contract, but discovery and storage need stronger encapsulation |
| `resolve()`, `_label()` | Path-oriented steps and user-facing errors | Useful small conveniences; delegate to read-only context |
| `encode()`, `decode()`, `matches()`, `output_fingerprint()` | `PathStep`, `Directory`, `Tests`, ordinary recorded values; binary/service kinds customize output identity | A coherent persistence/output-policy responsibility distinct from building |
| `publish()` | Specialized by `File` and `Directory` | Publication capability, not a substantive operation for every step |
| `report()` | Specialized by `Tests` | Result validation/presentation; importantly, this can fail the step |
| `teardown()`, `serve()` | Specialized by `Service` in reviewed production classes | Resource lifetime capability; defaults do nothing for ordinary values |
| `call_arguments()` | Engine dry output; customized by `Group`, `_Included`, `UserTask`, `Release` | Declaration presentation, not execution |
| `_reports_reused()` | `Group` and `_Included` | Composite-specific reporting policy on the universal base |
| `_cmd()`, `_check_cmd()`, `_command_env()` | Command-based checks, binaries, generation, packaging, evidence | Command execution service; not used by groups or user prompts |
| `_start_cmd()` | Niva's `JammerDevServer` and `WebDevServer`; `HttpService` customizes health readiness | Server/process capability on a base shared by non-process steps |
| `__new__()` | Every instantiation | Framework initialization machinery; retain its dataclass compatibility when moving metadata |

The split is visible without hypothetical subclasses:

- `Group` builds tuples of dependency values and keeps no record. It inherits command execution, server startup, and codecs it does not need in that role.
- `UserApproval` asks at the terminal, keeps no record, and uses `_label()`. It needs neither subprocess execution nor result codecs.
- `Check` and `Pytest` use `_cmd()` and inherit `Tests`' reporting/persistence behavior; they do not need a server-start API.
- `File`/`Directory` provide publication and content-aware persistence; their concrete subclasses may or may not run commands.
- `Service` owns stop/wait behavior and is non-reusable. Its instances inherit restoration APIs, but normal reuse never calls them.
- `Release` invokes module-level Git/Cargo helpers rather than `Step._cmd()`, showing that inheriting the large command helper does not itself establish a uniform execution boundary.

The five class flags are also distinct policies: `reusable`/`recorded` govern persistence and reporting, `deferred` governs activation, `once_per_run` affects requested-target scheduling, and `asks` controls exclusivity. They are engine-consumed class policy, not eight more instance-data concerns. Keeping declarative flags is reasonable; replacing every flag with another subclass would not improve cohesion automatically.

### Encapsulation problems that matter

**1. Private subclass state is implicitly declaration state.** `attributes()` scans `vars(self)` and excludes exactly eight engine fields. It does not exclude underscore-prefixed fields. A subclass assigning `self._cache = {}` gets a fingerprint-validation error; `self._counter = 1` silently contributes to its fingerprint; `self._helper = another_step` creates a dependency. Merely following the global `_` naming convention does not give a subclass private implementation state. `_Included` works around this by overriding `attributes()` to expose only `steps`, hiding `_path`, `_results`, and `_setup`.

Replace implicit discovery with the explicit `attributes()` contract selected below. Do not infer declaration membership from underscore prefixes: existing declarations may intentionally use those names. Private state affecting output must still be represented by an explicit input; hiding it must not create stale-cache reuse.

**2. Multiple modules can mutate identity without an ownership API.** `graph._name_steps` writes `variable`, `name`, `build_dir`, and `build_variables`; `run._apply_env` writes `env_values`; fingerprinting, persistence, and display read them independently. The class exposes no binding transition or read-only view. Reserved-name validation protects some declarations from collisions, but does not prevent arbitrary later assignment to these fields. For example, assigning an instance `name` is not rejected merely because `name` is reserved: that field already has to exist for engine use.

Bind loader metadata through one internal owner, freeze it after loading, and expose only the views needed by subclasses. Account for aliases, included files, derived names, and existing direct-construction tests before tightening mutation.

**3. The engine detects a capability by comparing method implementations.** `run.py` repeatedly tests `type(step).serve is not Step.serve` to decide stdin inheritance, lock release, reporting, and waiting. Merely adding a wrapper override changes scheduling/lifetime semantics, even if that wrapper only delegates to the no-op base implementation. An explicit serving capability/policy would communicate that contract more reliably than method identity. This is a stronger interface-segregation concern than the existence of no-op hooks alone.

**4. `_cmd()` dominates a declaration object's responsibilities.** It manages environment merging, subprocess creation, reader threads, buffering, cancellation, process registration, exit-status translation, and terminal output. These change for different reasons than dependency declaration or result serialization. `_start_cmd()` already delegates much of its work to `RunningProcess`; apply the same separation to ordinary commands. Keep compatibility wrappers small so existing subclass definitions remain readable.

### Recommended design direction

Use composition to separate ownership before introducing more inheritance:

1. **Declaration:** keep `Step[T]` focused on declared inputs/dependencies and `build(run)`, with small compatibility hooks where they make the DSL practical.
2. **Loader context:** own identity, source/build directory, declaration order, and build-file names together. Expose read-only label/path context where subclasses need it.
3. **Execution context:** own resolved environment, process runner, values, artifacts, and lifetime registration in the run. Retain `self._cmd(...)` initially as a thin adapter if changing every consumer is unnecessary.
4. **Result policies:** separate codec/matching/output identity from command execution. Preserve the useful `Tests`, `File`, `Directory`, and `Service` families; move mechanisms behind them rather than replacing the public DSL all at once.
5. **Capabilities:** make requested serving/resource behavior explicit where the engine needs to branch on it. Keep simple default hooks when they genuinely simplify the lifecycle; do not create a protocol for every no-op method.

This refines the earlier statement that optional hooks are reasonable: they can remain a convenient surface, while their implementations and state move to coherent owners. Uniform subclass usage is a diagnostic clue, not a requirement that every inherited method must be called by every subclass.

**Validation for a refactor:** Preserve dataclass and ordinary subclasses, custom attributes/dependencies, included results and aliases, cached/uncached steps, pure values, command steps, shared deferred services, and failure cleanup. Add explicit checks for private runtime state, environment release after success/failure, binding immutability, and serving capability behavior. No implementation changes or additional test runs were made for this review; evidence comes from subclass/consumer inspection and an AST inventory.

### Selected approach: explicit declaration through `attributes()`

**Author-selected direction:** Keep ordinary instance attributes and require an explicit `attributes()` implementation. Remove the base implementation that discovers declaration values through `vars(self)`. Do not introduce a separate declaration object for this change.

```python
class Compile(Step[Path]):
    def __init__(self, source: Input, optimize: bool = False) -> None:
        self.source = source
        self.optimize = optimize
        self._cache: dict[str, Path] = {}

    def attributes(self) -> dict[str, object]:
        return {
            "source": self.source,
            "optimize": self.optimize,
        }

    # Implement build(run) using the declared source and options.
```

Make `Step.attributes()` abstract. A concrete step must provide or inherit an explicit implementation; a step with no declared values returns `{}` deliberately. Subclasses that add build-relevant fields must extend the inherited declaration, including inherited options such as `copy_to`. Keep this method side-effect-free: it exposes declaration values without running commands or building dependencies.

Use this mapping as the common source for dependency discovery, fingerprint classification, parameter discovery, derived naming, and default dry-run arguments. Preserve explicit overrides such as `_Included.dependencies()` and presentation-specific `call_arguments()`, but require them to agree with the declaration. Continue validating declared value types and protecting engine-owned fields/hooks from collisions; removing reflection-based discovery does not authorize overwriting engine metadata.

Undeclared implementation state must neither affect fingerprints nor create dependency edges merely because it exists. Conversely, every configurable value, input, or dependency that affects the build must be declared. The tradeoff is explicit maintenance: adding an output-affecting field requires updating `attributes()`. Review and invalidation tests must catch omissions; do not silently restore `vars(self)` or dataclass-field discovery as a fallback.

**Migration and verification:** Update Roadie's concrete steps, test subclasses, and Niva consumers together. In particular, replace Niva's dynamically attached `snap_viewer.viewer_bundle` with an explicitly declared binary dependency before removing discovery. Verify inherited declaration composition, unchanged dependency order and dry output, parameter binding, and invalidation when each declared option/input changes. Verify that adding or mutating private runtime state does not change fingerprints, and that a concrete subclass missing `attributes()` fails clearly. Update the product specification's current “all instance attributes” contract as part of implementation. This records the chosen direction only; no code migration is included in the review.

### H1 — Highest priority: give command lifetime one owner

Roadie `8774aa2` (R14.6) changed both `_schedule`'s thread waits and `Step._cmd`'s subprocess wait to make interruption work. `3c6b308` then extracted `wait_interruptibly` and changed both `Service.serve` and `Step._cmd` to call it. `88ab47a` (R16.6) again crossed `_run_steps`, `Step._cmd`, and process/service handling to announce what an interrupt stops.

This is repeated maintenance pressure around the same lifecycle, not just initial wiring. The earlier extraction was useful, but command creation, registration, waiting, interruption, and cleanup still span owners.

**Opportunity:** Put command lifetime and cancellation mechanics behind a run-owned command/process facility. Let the scheduler decide which tasks may run and when cancellation begins; let the process facility guarantee stop/wait/cleanup; let `Step` delegate. Keep OS-specific mechanics in `system`. Do not move the scheduler into the process module or duplicate shutdown behavior in each step subclass.

**Verify:** Ordinary commands and requested/deferred services under single and multiple jobs, child processes, startup failure, and interruption. A future change to platform wait mechanics should not require editing the universal declaration class.

### H2 — Separate execution outcomes from their presentation

Roadie `376f3d5` (R17.1, run reports) added `_reports_reused` to `Step` and modified graph/run/CLI behavior. `e0ad58f` (R16.1) centralized labels across 13 changed paths. The same run/step pair also changed for output prefixes (`6b01434`). Reporting features therefore reach into declaration and composite-step behavior, not only a renderer.

**Opportunity:** Have execution produce a structured outcome containing step identity, reuse/build status, timing, and failure. Use that outcome for terminal and report rendering. Compute composite reuse once in the execution/composition policy, rather than requiring a universal hook plus printing inside `Group.build` and `_Included.build`. Keep `Tests.report`'s failure validation distinct from a passive output sink: it currently determines success, so moving it into optional reporting would be incorrect.

**Verify:** Grouped reuse, included defaults, failed test results, deferred services, and report-write failure. Terminal output and JSON reports should agree without changing subclass declarations when a presentation format changes.

### H3 — Consolidate common execution stages, not all CLI and graph code

The CLI/run pair changed for multi-results (`8937e82`), parameters (`aef7dcd`), setup (`e7930c2`), parallelism (`53f188d`), and dry execution (`eb0beaf`). Some coupling is expected: adding a CLI option naturally changes its consumer. More specifically, `aef7dcd` added `current_step(...)` independently around both `_run_one` and `_start_one`; execution-context changes must remember both paths.

**Opportunity:** Introduce one scoped step-invocation operation for context binding, timing, cancellation/error translation, and build invocation, while preserving different deferred/publication semantics. Keep argument parsing in the CLI. Put selection validation and the scheduled plan in the engine, with an explicit plan/identity contract consumed by execution. This reinforces G5 and the explicit `attributes()` decision; co-change does not justify combining CLI, graph, and executor into one class.

**Verify:** Parameter context on immediate and deferred paths, setup ordering, aliases, multiple requested results, and invalid direct-engine requests. Confirm that contexts are released on failure.

### H4 — Share input policy between check runners; retain different result policies

Roadie `7ff359c` changed both `Check.__init__` and `Pytest.__init__` to accept steps alongside inputs, repeating the same accepted-type union and normalization policy. `8b4cc6d` changed their one-or-many behavior; `b6eb764` changed captured-output behavior. `one_or_many` already shares mechanics, so the remaining duplication is the meaning of a check's inputs and command-output options.

**Opportunity:** Use a narrow shared input-normalization function/type contract and the command facility from H1. Adopt the explicit declaration method consistently so later changes to supported inputs cannot leave one runner behind. Keep pytest's JUnit and exit-code semantics separate from generic command pass/fail behavior. The history supports small shared functions, not a large command-test inheritance hierarchy.

**Verify:** Mixed inputs and steps, generators, invalid members, nonzero exit, missing/malformed test reports, and streamed/captured output.

### H5 — Make Niva artifact and mutable-cache dependencies explicit

Niva `6507772` replaced a viewer-bundle `Check` with `ViewerBundle(Directory)` and rewired the binary/web dependencies. This is a healthy change: the producer now describes its artifact, rather than consumers assuming an external directory exists. The build/steps pair also includes framework migrations (`7970a13`, `81c07a8`) and initial service integrations, so its eight co-changes do not establish that the two files belong together.

Niva `f2f4802` independently added `--cache-dir target/mypy/forge` and `--cache-dir target/mypy/ops` after shared caches caused a mypy crash. This reveals an execution resource absent from a plain command string: mutable tool cache ownership under concurrent runs.

**Opportunity:** Preserve build files as composition and custom classes as behavior. Replace dynamic binary dependency attachment with an explicit declared dependency as already selected. For repeated mypy invocations, use a small Niva helper that assigns distinct cache directories from stable gate identity. Only generalize to Roadie if other tools demonstrate the same resource contract; serializing every check would hide the problem and sacrifice parallelism.

**Verify:** Cold viewer generation before compilation, invalidation after web-source changes, and simultaneous forge/ops type checking with distinct cache ownership.

### H6 — Preserve the packaging/evidence boundary that history already repaired

Niva `f18256d` moved universal-binary validation from `PackagesBuilt` evidence into `CliPackage._macos` via `require_archs`. `6026f2e` consolidated archive/installer names in `cli_archive`, `editor_installers`, and `release_packages`, with evidence consuming those functions. Both co-changes remove duplicated knowledge rather than expose a need to merge modules.

**Opportunity:** Keep artifact correctness in producers and observation of CI/release outcomes in evidence. Consolidate the remaining duplicate workspace-version reader (finding 10), but do not restore validation that works only when an acceptance/evidence step happens to run.

**Verify:** Calling a package step directly rejects an invalid artifact; changing the shared naming policy updates producer and evidence expectations together.

### H7 — A file can contain several change clusters even without cross-file churn

Roadie's `build/release.py` changed in eight qualifying commits. Its history separates message behavior (`e921c09`), Cargo support (`f73a1a2`), package.json support (`9bd1929`), newline preservation (`e5a1938`), and directory-source discovery (`357db48`). Retain the useful shared I/O extraction; avoid making each format reimplement it. This reinforces finding 8 with distinct historical reasons to change, rather than module size alone.

**Verify:** Format-preserving edits and directory discovery independently of Git, then end-to-end release failure/recovery tests around the publication boundary.
